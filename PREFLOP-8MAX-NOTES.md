# Preflop 8-max constructed ranges (v1.3) — derivation notes + host runbook

Status: code + config + tests written on branch `preflop-8max` (issue #3).
Generation itself runs on the host (see the runbook at the bottom) — the
sets under `data/preflop/sets/` are **not** regenerated by this change.

## Honesty first

- **No published 8-max PLO4 chart exists and no solver library offers a
  standard 8-max cash set.** GTO Wizard offers only Straddle /
  Straddle+Ante at this table size (verified 2026-11-17). There is
  therefore **no cross-check target** for 8-max: these sets are pure
  labelled derivations, exactly like the 9-max family before them.
- Every 8-max set is a CONSTRUCTED set (never GTO, never solver output).
  Its provenance cites **no sources** (`sources: []`) and states the
  derivation in `provenance.derivation`; every set records its `rake`
  variant (`raked` / `no-rake`), and every config target carries
  `kind: "derived"`.
- Derivation text recorded on every 8-max set: *"derived-by-mapping:
  targets derived from the same rake variant's 6-max targets by the
  players-behind seat mapping; no published 8-max PLO4 chart exists
  (GTO Wizard offers no standard 8-max cash set - Straddle /
  Straddle+Ante only) and none is cited as a source."*

## The mapping (players-behind equivalence)

The 9-max derivation's principle: a seat's opening width is governed by
how many players act behind it. 8-max seats in action order, with
players behind:

| 8-max seat | behind | takes the values of | why |
|---|---|---|---|
| UTG | 7 | 9-max UTG+1 (raked) / stepped-down anchor (no-rake) | no 6-max seat has 7 behind |
| UTG+1 | 6 | 9-max UTG+2 (raked) / stepped-down anchor (no-rake) | no 6-max seat has 6 behind |
| MP | 5 | 6-max UTG | same behind-count as 6-max UTG |
| HJ | 4 | 6-max MP | same behind-count as 6-max MP |
| CO | 3 | 6-max CO | unchanged seat |
| BTN | 2 | 6-max BTN | unchanged seat |
| SB | 1 | 6-max SB | unchanged seat (raise-or-fold play) |
| BB | 0 | — | never opens |

Each variant derives from **its own** 6-max anchors: raked from the
raked 6-max targets, no-rake from the GTO Wizard cEV-anchored no-rake
targets.

**Responses** (BB vs all seven opens, SB vs the six non-blind opens,
BTN vs HJ/CO — the `btn_vs` list is the 4- and 3-behind seats, the same
slots as at 6-max):

- Carried seats keep their response values outright (e.g. BB vs BTN is
  the 6-max BB vs BTN in both variants).
- Raked: responses follow the opener's mapped slot, with the 9-max
  derivation's own slot compression — MP and HJ share the vs-MP slot
  (the 9-max derivation likewise gave both its 0.18-wide LJ and its HJ
  the vs-MP defense values), UTG+1 takes the 6-max vs-UTG values, and
  UTG takes the 9-max derivation's vs-UTG+1 values (its tightest slot).
- No-rake: responses follow the opener's mapped seat strictly
  (BB vs MP = no-rake BB vs UTG, BB vs HJ = no-rake BB vs MP, …); the
  two new seats step down (below).

**The two new seats in the no-rake variant** have no 9-max counterpart
(9-max is raked-only), so they step down from the no-rake 6-max UTG
anchor by the raked curve's per-step ratios: RFI −2.0pp per extra
player behind (UTG+1 16.5%, UTG 14.5%); BB defense call ×0.872 then
×0.920, three_bet ×0.754 then ×0.930; SB defense call ×0.857 then
×0.933, three_bet ×0.800 then ×0.900. In the raked variant the same
seats instead take the 9-max derivation's same-behind-count values
outright (RFI 16% / 14%, bands 15–17 / 13–15).

**Continuations**: the same three matchups as 6-max (BTN vs BB, BTN vs
SB, CO vs BTN), built against each variant's own 8-max sets with the
v1.1 internal parameters (continue 0.5 of the open; of the continue,
call 0.82 / four_bet 0.18; 4000 samples). Labelled `internal`, never
externally validated — same as every continuation family.

## Set list and counts

Per variant: 7 RFI + 15 responses (BB 7, SB 6, BTN 2) + 3 continuations
= **25 sets**. Two variants = **50 new sets**. Library total after
generation: 63 existing + 50 = **113 sets**.

ID scheme (mirrors the v1.2 family naming): raked prefix
`constructed-v1.3-8max`, no-rake prefix `constructed-v1.3-8max-norake`;
then `-<pos>-rfi` (SB: `-sb-sbplay`), `-<resp>-vs-<opener>`,
`-<continuer>-vs-<three-bettor>-3bet`. Example ids:
`constructed-v1.3-8max-utgplus1-rfi`,
`constructed-v1.3-8max-norake-bb-vs-sb`,
`constructed-v1.3-8max-btn-vs-bb-3bet`.

## Implementation shape

- Config: new file `data/preflop/ranges-config-v1.3.json` (v1/v1.2
  configs untouched; every v1.2 field carried over byte-identical in
  meaning). New top-level `eightmax` section:
  `{ btn_vs, raked: {rfi_targets, response_targets, continuations},
  norake: {rake_note, rfi_targets, response_targets, continuations} }`,
  plus `derivation_note_8max`. The v1.3 config is now the canonical one
  (`build-ranges` defaults to it).
- Engine (`ranges.rs`): `POSITIONS_8MAX`; optional `eightmax` section
  on `RangesConfig` (absent in v1/v1.2 configs — they parse and
  generate exactly as before); a generation stage after the no-rake
  stage builds both variants with the existing styled builders;
  `check_doc_totals` resolves 8-max targets from the section;
  `continuation_matchup` searches the 8-max sections;
  `build_continuation_set_styled` takes the table size explicitly
  (existing callers pass `"6max"`, behaviour unchanged).
- Seed discipline: master seed unchanged (5046601). New Monte Carlo
  stream bases, all disjoint from the existing ranges (opener tags stay
  ≤ ~111k on top of each base): raked 8-max openers 300_000,
  continuations 1_100_000; no-rake 8-max openers 1_300_000,
  continuations 1_500_000.
- Schema: `table_size` gains `"8max"` with its position list
  (allOf branch) and a v1.3 amendment note.
- UI: `TableSize` gains `'8max'`; the `TABLE_SIZES` guard list gains it
  too (without that, the shape guards reject the whole index — the
  v1.2 silent-drop lesson); `POSITION_ORDER['8max']`; the Preflop page
  gains the 8-max pill; the rake hint copy states the derivation for
  both variants. `groupSets`/selection were already table-generic.
- Tests (`ranges_validation.rs`): config/mapping assertions (counts,
  all-derived kinds, seat-mapping equalities against the 6-max/9-max/
  no-rake targets, v1.2 sections unchanged, v1.2 config has no
  `eightmax`), RFI builds for both variants (ids, `table_size`,
  provenance sources empty + derivation present, achieved ≤ 0.5pp,
  schema validation), one response + one continuation per variant
  (continuation doc records `table_size: "8max"`; `continuation_matchup`
  resolves the 8-max id).

## Judgement calls

1. **Version stem `v1.3` in the ids** (not a v1.2-style suffix): the
   family is introduced by config v1.3, following the precedent that a
   family's stem names its introducing config version.
2. **One `eightmax` section with per-variant target maps**, mirroring
   the `norake_6max` optional-section pattern, instead of adding
   `"8max"` keys to the top-level table-keyed maps — the top-level maps
   are raked-only, and the no-rake variant needs its own home anyway.
3. **Raked new-seat values come from the 9-max derivation** (the only
   raked precedent for 6/7-behind seats) rather than a fresh
   extrapolation; **no-rake new seats use ratio step-downs** from the
   no-rake UTG anchor because no no-rake 9-max derivation exists.
4. **Raked response slot compression** (MP/HJ share vs-MP) follows the
   9-max derivation's demonstrated behaviour; the no-rake variant maps
   responses strictly by mapped seat, since its own anchors define
   every slot it needs.
5. **BTN `btn_vs` = HJ, CO** at 8-max: the 4- and 3-behind seats, the
   same slots the 6-max BTN responds from.
6. Both 8-max families cite **no sources at all** — not even the GTO
   Wizard cEV source the no-rake 6-max family cites — because no 8-max
   totals were checked against anything; the derivation is the whole
   provenance.

## Host runbook (run on the host, from the repo root)

Snapshot discipline first: the 63 existing sets must regenerate
byte-identical `hands`. Snapshot BEFORE, compare AFTER.

```sh
# 0. Snapshot the existing sets' hands hashes (63 sets)
python3 - <<'EOF'
import hashlib, json, pathlib
out = {}
for p in sorted(pathlib.Path("data/preflop/sets").glob("*.json")):
    d = json.loads(p.read_text())
    out[d["id"]] = hashlib.sha256(
        json.dumps(d["hands"], sort_keys=True).encode()
    ).hexdigest()
pathlib.Path("/tmp/pre-8max-hands-hashes.json").write_text(json.dumps(out, indent=1))
print(len(out), "sets snapshotted")
EOF

# 1. Build + validate the code
cargo build --release -p plo-solve --bin build-ranges
cargo test --release -p plo-solve --test ranges_validation

# 2. Generate with the v1.3 config (the new build-ranges default)
cargo run --release -p plo-solve --bin build-ranges

# 3. Check mode: totals vs config targets, schema, index consistency
cargo run --release -p plo-solve --bin build-ranges -- --check

# 4. Verify the snapshot is unchanged and the index grew to 113
python3 - <<'EOF'
import hashlib, json, pathlib
before = json.loads(pathlib.Path("/tmp/pre-8max-hands-hashes.json").read_text())
after = {}
for p in sorted(pathlib.Path("data/preflop/sets").glob("*.json")):
    d = json.loads(p.read_text())
    after[d["id"]] = hashlib.sha256(
        json.dumps(d["hands"], sort_keys=True).encode()
    ).hexdigest()
changed = [k for k in before if after.get(k) != before[k]]
print("existing sets changed:", changed or "none")
idx = json.loads(pathlib.Path("data/preflop/index.json").read_text())["rangesets"]
print("index entries:", len(idx), "(expect 113)")
e8 = [e for e in idx if e["table_size"] == "8max"]
print("8max entries:", len(e8), "(expect 50)")
assert all(e.get("rake") for e in idx), "every index entry carries rake"
assert sum(1 for e in e8 if e["rake"] == "raked") == 25
assert sum(1 for e in e8 if e["rake"] == "no-rake") == 25
# The derivation labelling lives in the set documents' provenance
# (index entries carry only a method/version/hash summary).
for e in e8:
    d = json.loads(pathlib.Path("data/preflop", e["path"]).read_text())
    prov = d["provenance"]
    assert prov["derivation"], f"{e['id']}: derivation missing"
    assert prov["sources"] == [], f"{e['id']}: derived sets cite no sources"
    assert d["rake"] == e["rake"] and d["table_size"] == "8max"
print("index + 8-max provenance invariants OK")
EOF

# 5. UI build (typecheck + bundle)
cd ui && npm run build
```

## Caveats / out of scope

- The API's `continuationBase()` helper (`api/server.mjs`) derives
  continuation base ids with v1.1-style naming only; the no-rake
  continuations were already not wired through it, and the 8-max
  continuations have the same status. Wiring them is a separate lane
  if wanted.
- The Runner / spot-catalog table sizes (`tools/build_spot_catalog.py`,
  Runner page) are the postflop library system, not the preflop range
  library — untouched.
- The Starting Hands study page (separate lane, not in this tree)
  reads the preflop index generically, so it picks up the 8-max sets
  automatically once the regenerated index lands — no change needed
  there beyond its own table-size admission if it keeps a list.
